## 一、监听器（Listener）概述

监听器是 JMeter 的**数据采集和展示组件**，负责收集、展示和分析测试执行过程中的采样结果。

### 核心理念

```
采样器 (Sampler) → 生成结果 → 监听器 (Listener) → 展示/存储
```

**重要规则：**
- 监听器可以放在**测试计划**、**线程组**、**采样器**任意层级
- 放在哪个层级就收集该层级及以下的所有采样结果
- GUI模式下监听器消耗大量内存，**CLI模式下建议只保留简单数据写入器**
- 多个监听器可以并存，互不影响

## 二、5 种核心监听器详解

### 1. 聚合报告（Aggregate Report）⭐最常用

| 字段 | 含义 | Day 2 实测值 |
|------|------|-------------|
| Label | 采样器名称 | GET-获取帖子列表 等 |
| Samples | 请求总数 | 50（每个采样器） |
| Average | 平均响应时间(ms) | 257ms（总） |
| Median | 中位数响应时间 | 232.5ms |
| 90% Line | 90%请求的响应时间 | 469ms |
| 95% Line | 95%请求的响应时间 | 627.9ms |
| 99% Line | 99%请求的响应时间 | 960.3ms |
| Min | 最小响应时间 | 18ms |
| Max | 最大响应时间 | 1479ms |
| Error % | 错误率 | 20.0%（仅404） |
| Throughput | 吞吐量(req/s) | 26.2/s |
| Received KB/sec | 接收速率 | 181.6 KB/s |
| Sent KB/sec | 发送速率 | 3.7 KB/s |

**使用场景：** 压测结束后看总体指标，判断系统性能瓶颈。

**关键判据：**
- Average < 预期阈值 → 合格
- 90% Line 比 Average 更能反映真实用户体验
- Error% > 0% → 排查失败请求

---

### 2. 汇总报告（Summary Report）

聚合报告的**精简版**，字段更少：

| 字段 | 说明 |
|------|------|
| Label | 采样器名称 |
| Samples | 请求数 |
| Average | 平均响应时间 |
| Min / Max | 最小/最大响应时间 |
| Std. Dev. | 标准差（反映响应时间离散程度） |
| Error % | 错误率 |
| Throughput | 吞吐量 |
| Avg. Bytes | 平均响应大小(bytes) |

**与聚合报告的区别：**
- 没有 90%/95%/99% 分位数
- 多了 Std.Dev.（标准差）和 Avg.Bytes
- 适合**大量数据场景**（内存占用更低）

---

### 3. 察看结果树（View Results Tree）

**调试神器**，能看到每个请求的完整细节：

| Tab | 内容 |
|-----|------|
| Sampler result | 请求基本信息（URL、方法、响应码、耗时、字节数） |
| Request | 发送的请求内容（Headers、Body） |
| Response data | 服务器返回的响应内容 |

**⚠ 注意：**
- GUI模式下才有效，CLI模式下基本无用
- 会保存所有响应数据，**压测时务必关闭**否则内存爆炸
- 适合脚本调试阶段，正式压测前移除

---

### 4. 图形结果（Graph Results）

实时可视化展示，包含4个指标：

| 指标 | 含义 |
|------|------|
| 黑色曲线 | 当前吞吐量（Data = 实际值） |
| 蓝色曲线 | 平均吞吐量（Average） |
| 红色曲线 | 中位数（Median） |
| 绿色曲线 | 偏离值（Deviation） |

**使用场景：**
- 观察TPS随时间变化趋势
- 判断系统是否达到稳态
- GUI实时监控

---

### 5. 断言结果（Assertion Results）

**只显示断言失败的请求**，成功的请求不显示。

> 💡 今天是Day 2还没讲断言，所以这个监听器暂时不会显示内容。Day 4学了断言后，失败的断言就会出现在这里。

**核心价值：** 快速定位哪些请求没通过业务校验，不用在几千条结果里翻找。

---

### 6. 后端监听器（Backend Listener）—进阶

将测试数据实时发送到**时序数据库**（InfluxDB / Graphite），再用 **Grafana** 可视化。

```
JMeter → Backend Listener → InfluxDB → Grafana（实时大盘）
```

**配置要点：**
| 参数 | 值 | 说明 |
|------|-----|------|
| backend listener class | InfluxdbBackendListenerClient | 后端类型 |
| influxdbUrl | http://localhost:8086/write?db=jmeter | InfluxDB地址 |
| summaryOnly | true | 只发汇总数据，不发每条采样 |
| percentiles | 90;95;99 | 发送哪些分位数 |
| testTitle | Day2_Listener_Test | 测试标识 |

**企业级用法：** Jenkins + JMeter + InfluxDB + Grafana 四位一体，全链路性能监控。

## 三、监听器使用建议

| 阶段 | 推荐监听器 | 原因 |
|------|-----------|------|
| 脚本调试 | 察看结果树 + 断言结果 | 需要看请求响应细节 |
| 基准测试 | 聚合报告 + 图形结果 | 分析性能基线 |
| 正式压测(CLI) | 简单数据写入器 + 后端监听器 | 保存结果 + 实时大盘 |
| 压测后分析 | HTML报告（-e -o） | 可视化+统计 |

**CLI模式黄金组合：**
```
-l result.jtl          ← 保存原始结果
-e -o report/          ← 生成HTML报告
+ 后端监听器           ← 实时大盘
```

## 四、Day 2 实测数据

### 测试配置
- 线程数：10 | Ramp-Up：3s | 循环：5次
- 总样本数：250（5个采样器 × 50次）
- 运行时长：约10秒

### 各接口表现

| 接口 | 样本数 | 错误率 | 平均响应 | 中位数 | 90%Line | 吞吐量 |
|------|--------|--------|----------|--------|---------|--------|
| GET-获取帖子列表 | 50 | 0% | 430.9ms | 418.5ms | 668.8ms | 5.7/s |
| GET-获取单条帖子 | 50 | 0% | 250.6ms | 219.0ms | 251.9ms | 6.0/s |
| POST-创建帖子 | 50 | 0% | 342.4ms | 314.0ms | 401.8ms | 5.9/s |
| GET-百度首页 | 50 | 0% | 26.7ms | 23.0ms | 43.0ms | 6.2/s |
| GET-故意404 | 50 | 100% | 234.9ms | 220.5ms | 257.9ms | 6.1/s |
| **总计** | **250** | **20%** | **257.1ms** | **232.5ms** | **469.0ms** | **26.2/s** |

### 关键发现
1. **百度首页最快**（26.7ms）— 静态页面 + CDN加速
2. **帖子列表最慢**（430.9ms）— 返回100条数据，数据量大
3. **404请求虽然失败但不影响其他请求** — 线程组设了 `continue`
4. **20%错误率完全来自404场景** — 符合预期
