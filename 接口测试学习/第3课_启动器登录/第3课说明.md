## 🔍 接口是怎么拿到的

**没用抓包工具，也没装证书。**

你之前说不会抓包——其实这次压根不用学。因为启动器自己把每个 HTTP 请求**明文写进了日志**：

```
C:\Users\Administrator\AppData\Local\Raptor-Test\Logs\launcher-*.log
```

日志里有 `[DETAIL] HTTP Request >>> / HTTP Response <<<` 段，Method、URL、Header、Body 全都在。把 47 个日志扫一遍，接口就全出来了。

`工具\抓日志接口.py` 就是干这个的，以后接口改了，重跑一次就知道。

## 🏗 登录链路的真实结构

| 环节 | 地址 | 说明 |
|---|---|---|
| **登录** | `POST http://<网关地址>:9511/` | 头 `CID: 1396`，body 是 protobuf |
| **换 access token** | 同上，`CID: 1401` | body = 登录返回的 token |
| **远程配置** | `GET http://<网关地址>:9000/raptor-client-test/...` | 静态 CDN，返回版本号 |
| **游戏清单** | 同上 `.../Manifest.json` | 附带 `.md5` 可做完整性校验 |

网关用 HTTP 头里的 **CID** 做消息路由：

- `1396` 登录
- `1401` 换 access token
- `1527` 公告
- `1409` 心跳
- 不存在的 CID → `HTTP 500  no route for cid 9999`
- 不带 CID → `HTTP 500  no route for cid -1`

## ⚠️ 两个必须记住的坑

### 坑 1：日志里的请求体**少一个字节**

日志把 body 当字符串打印，而 protobuf 字段 1 的标签恰好是 `0x0A` —— **就是换行符，被日志吃掉了**。

照抄日志的 body 发出去，会得到 `code=38`（参数错误），查半天查不出来。

```
日志里看到：  [长度][账号] [0x12][长度][密码] ...
真正要发的：  0x0A [长度][账号] [0x12][长度][密码] ...
              ↑ 补这个
```

用例 **A14 / B03** 就是专门守这个坑的。

### 坑 2：token 会被新登录顶掉（单会话互踢）

- token 按**秒**派生，同一秒内重复登录拿到的是同一个 token
- **一旦发生一次产生新 token 的登录，旧 token 立即作废**
- 拿旧 token 去换 access token → `HTTP 499` + `code=35`

这解释了启动器为什么在拉起游戏前**一定要再刷一次 token**。

用例 **B06 / B07** 覆盖这个机制。写自动化时也要遵守：**用之前先刷**。

## ★ 这一课最重要的一件事

报告里所有报错，**HTTP 状态码几乎都是 200**。

| 输入 | HTTP | 响应体 code |
|---|---|---|
| 密码错误 | 200 | 14 |
| 账号不存在 | 200 | 13 |
| 账号为空 | 200 | 39 |
| 密码为空 | 200 | 10 |
| 协议字段缺失 | 200 | 38 |
| 旧 token / 伪造 token（字段可解析） | **499** | 35 |
| 不存在的 CID | **500** | （纯文本） |
| GET 方法 | **501** | （纯文本） |

所以脚本里**绝对不能**用 `assert r.status_code == 200` 判断用例通过——那是自欺欺人。

必须断言响应体里的 `code`。这就是第 1 课那句"请求发通了没有毫无意义"在真实项目里的样子。

## ★ 第二个坑：别把 499 当成"限流"乱重试

我一开始在 `run_tests.py` 里写了这么个"聪明"的重试逻辑：

```python
if last.status_code in (499, 502, 503, 504):
    time.sleep(...); continue   # 当作限流，退避重试
```

**这是错的。** 实测数据打脸：

| 请求体 | HTTP | body | 说明 |
|---|---|---|---|
| `0x0A` + `"A"×44` | **499** | `08 23` → code=35 | token 字段**能解析**，值无效 |
| 去掉 `0x0A` 的 44 个 A | **200** | code=1 | token 字段**解析不出来** |
| `0x0A` + 空串 | **499** | code=35 | 字段能解析，值为空 |
| 空 body | **200** | code=1 | 完全无字段 |

- **同一伪造 token，间隔 1.5 秒连打 8 次，8 次全是 499** —— 确定性行为，和频率无关。
- 我又跑了 40 次错误密码、30 次高频正确登录、15 个不同账号，**完全没有触发任何限流**。

所以 499 的真实含义是：**"token 字段可解析但验证失败"** —— 网关在协议层直接拒绝，不再往下走业务逻辑。

**教训**：重试逻辑必须建立在"确认这是瞬时抖动"的基础上。看到 499 就重试，等价于**用一个错误假设掩盖了真实的协议行为**，最后表现为用例判定莫名其妙地飘。只对 502/503/504（真正的服务端故障）重试才安全。

### 顺手发现的几个问题

写用例过程中撞到这几处，建议提给开发：

1. **A10 账号大小写敏感** —— `WUYAN233` 被判为"账号不存在"，玩家输错大小写时错误提示会误导（应提示"账号或密码错误"而不是"账号不存在"）
2. **A11 账号前后空格未 trim** —— 手机端复制粘贴常带空格，建议服务端做 trim
3. **A15/A16 版本号完全不校验** —— 传空、传 `9.9.9` 都能登录成功，版本门槛没生效
4. **A17 昵称字段可任意伪造** —— 客户端传的昵称服务端照单全收（当前返回的是账号数据，风险低，但字段本身是无效的）
